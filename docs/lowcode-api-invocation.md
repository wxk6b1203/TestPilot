# 低代码按接口 ID 调用与自动封装（完整方案）

> 状态：本方案为实施依据，与 `docs/design.md` §6 互补。目标不是 MVP，而是
> “接口目录变更 → 低代码脚本无需改动，下次运行自动获得最新封装”的完整闭环。

## 1. 问题与目标

现状（v2）低代码只有 `ctx.http(method, uri, ...)` 与 `HttpAPI(method, uri)`：
URI/method 等定义在脚本里被复制，接口目录中的 cookies / TLS 设置 / 证书 /
comment_tolerant_json / binary_ref / pre/post 脚本全部丢失；接口变更不会传播。

目标：

1. `ctx.http_api("123").run(...)` / `ctx.grpc_api("456").run(...)` / `ctx.api("123")` 按 ID 调用；
2. 派发时自动生成 `tp_api_wrappers.py`（稳定别名 `Api<ID>` + 可读别名），新增/改动接口后下次运行自动生效；
3. 按 ID 调用与声明式 `api_call` 共享同一条执行语义；
4. `ctx.http(...)` 保留为低层逃生通道（目录外/临时/压测行为脚本）。

## 2. 总体数据流

```
用户保存接口/用例
   │  接口只写 DB，不生成静态文件
   ▼
Scheduler.materializeCase(lowcode)
   ├─ script_ref → source（既有）
   ├─ 合并依赖：definition.http_api_refs/grpc_api_refs（显式）
   │             + 源码静态提取（ctx.http_api("123")、Api123 等）
   │             + from tp_api_wrappers import 且无任何 refs → 项目内全部接口（受限）
   ├─ 租户隔离解析：HttpApi/GrpcApi 快照 → FunctionalTask.http_apis / grpc_apis
   ├─ binary_ref 联动：被引用接口体内的 artifact:<id> → inline_files
   └─ GenerateAPIWrappers() → FunctionalTask.api_wrappers_source
   ▼
Worker._run_lowcode
   ├─ 写 scratch/tp_api_wrappers.py
   ├─ payload 注入 http_api_ids / grpc_api_ids（ctx.api 判别）
   └─ bridge op=api_request → LowCodeApiCaller（HTTP/gRPC 快照执行）
   ▼
沙箱脚本
   import tp_api_wrappers / ctx.http_api / ctx.api
```

## 3. 契约（proto）

`testpilot/common/v1/types.proto`：

```proto
message LowCodeCase {
  oneof script { string script_ref = 1; string source = 2; }
  string entry = 3;
  google.protobuf.Struct parameters = 4;
  repeated string http_api_refs = 5;   // 接口依赖声明（HTTP api id）
  repeated string grpc_api_refs = 6;   // 接口依赖声明（gRPC api id）
}
```

`testpilot/worker/v1/worker.proto`：

```proto
message FunctionalTask {
  TestCase case = 1;
  string case_result_id = 2;
  map<string, GrpcApi> grpc_apis = 3;
  map<string, bytes> inline_files = 4;
  map<string, HttpApi> http_apis = 5;          // 低代码 http_api_refs 解析后的快照
  string api_wrappers_source = 6;              // 自动生成的 tp_api_wrappers.py（可空）
}
```

依赖声明使用显式字符串数组而不是单一 `api_refs` 结构：JSON 形态简单（前端/Copilot
易生成），HTTP/gRPC 分表分映射，避免 ID 歧义。雪花 ID 全局生成，正常不会跨表重复；
若手工制造出同 ID 双类型，派发直接报错（明确优于静默选错）。

## 4. Scheduler 侧

### 4.1 依赖合并（materializeCase 时）

- 显式 refs：`LowCodeCase.http_api_refs` / `grpc_api_refs`；
- 静态提取（纯字符串常量）：
  - `ctx.api("123")` / `ctx.http_api('123')` / `ctx.grpc_api("123")`；
  - `HttpAPI(api_id="123")` / `GrpcAPI(api_id="123")`；
  - 脚本出现 `tp_api_wrappers` import 时提取 `Api123` 标识符；
- 兜底：脚本 import 了 `tp_api_wrappers` 且显式+提取均为空 → 拉取**本项目全部接口**
  （上限 200；超限报错要求显式声明 refs）；
- 动态 ID（`getattr(tp_api_wrappers, f"Api{id}")`）必须显式声明 refs，否则运行时报
  清晰错误。

### 4.2 解析与校验

- HTTP：`tenant_id = ? AND id IN ?`，生成 `map[string]*HttpApi`；
- gRPC：同 `resolveGrpcRefs`，进 `task.functional.grpc_apis`；
- 任一 ref 不存在 → case_result 置 FAILED（复用既有派发失败路径）；
- 同一 ID 同时声明为 HTTP 与 gRPC 且两表均命中 → 报错；
- 被引用 HttpApi 体内的 `binary_ref` 参与 `resolveInlineFiles`（artifact 内联，≤8MiB）。

### 4.3 封装生成器（确定性）

生成文件：`tp_api_wrappers.py`。

```python
# auto-generated by TestPilot — do not edit
from testpilot_sdk import GrpcAPI, HttpAPI

class Api123(HttpAPI):
    """创建用户 · POST /users"""
    api_id: str = "123"
    method: str = "POST"
    uri: str = "/users"
    params: dict = {"page": 1}
    headers: dict = {"X-Trace": "{{trace}}"}
    cookies: dict = {}

class Api456(GrpcAPI):
    """echo · testpilot.echo.v1.EchoService/Echo"""
    api_id: str = "456"
    full_service: str = "testpilot.echo.v1.EchoService"
    method: str = "Echo"
    request: dict = {"message": "hi"}
    metadata: dict = {}

CreateUser = Api123
Echo = Api456
```

规则：

- 每个接口都有稳定类名 `Api<ID>`，永不因改名/换目录变化；
- 可读别名由接口名派生（PascalCase、非法字符清理、保留字避让、重名追加 `_2`）；
- method/uri/headers 等**生成在类字段默认值中，仅作文档/补全**；SDK `run()` 只发送
  显式设置字段（Pydantic `model_fields_set`），类默认值不会成为 override，因此接口
  变更后旧默认值也不会覆盖新快照——执行永远以派发时接口快照为准；
- 排序按 ID，输出确定性（测试可断言）；
- 别名查找：优先 `http_apis.name` / gRPC 目录树节点名，兜底 `Api<ID>`。

### 4.4 REST 预览

`GET /api/v1/projects/:id/api-wrappers`（viewer）：
- 默认返回项目全部 HTTP+gRPC 接口的封装源码；
- 可选 `http_ids=1,2` / `grpc_ids=3` 只生成指定接口；
- 响应：`{"source": "...", "count": n}`；前端“封装预览”复用同一生成器。

### 4.5 前端

- 低代码用例编辑器新增“接口依赖”多选（项目 HTTP/gRPC 接口，保存进
  `definition.http_api_refs` / `grpc_api_refs`）；
- 接口页增加“封装预览”，显示当前项目（或选中接口）生成的 wrapper 源码；
- 保持可编辑区仍为脚本源码，生成文件不落库、不手改。

## 5. Worker / SDK 侧

### 5.1 SDK API 面

```python
# 按 ID（推荐，业务参数通过 kwargs/实例字段覆盖）
resp = await ctx.http_api("123").run(body={"name": "neo"}, params={"page": 1})
gresp = await ctx.grpc_api("456").run(request={"message": "hi"}, metadata={"trace": "x"})
resp = await ctx.api("123").run(...)            # 自动判别 HTTP/gRPC

# 自动生成封装（等价，可读性更好）
from tp_api_wrappers import Api123, CreateUser
resp = await Api123().run(body={"name": "neo"})
```

- `HttpAPI(api_id=...)` / `GrpcAPI(api_id=...)`：`api_id` 存在时走桥 `api_request`；
- `HttpAPI` 兼容旧用法（无 `api_id` 时退化为 `ctx.http` 桥路径）；
- `run()` 只发送**显式设置**的字段（Pydantic `model_fields_set`），避免默认值覆盖
  接口快照；
- override 语义与声明式 `HttpOverride` 一致：headers/params/cookies 按键合并，body
  整体替换，method/uri 整体替换；`tls_verify` / `follow_redirects` 不允许脚本覆盖
  （安全设置以接口快照为准）；
- 入口 `run(ctx)` 的 ctx 存入 contextvar，`HttpAPI.run()` 可拿到当前 ctx 的变量
  快照并在 pre/post 脚本写入后合并回 `ctx.vars`；
- `Response` 增加 `api_id` / `request` 快照字段；新增 `GrpcResponse`。

### 5.2 桥操作 `api_request`

请求：

```json
{"op": "api_request", "args": {
  "kind": "http|grpc",
  "api_id": "123",
  "vars": {"user": "neo"},
  "overrides": {"method": null, "uri": null, "headers": {}, "params": {},
                "cookies": {}, "body": null, "binary_ref": null,
                "request": {}, "metadata": {}}
}}
```

响应：

```json
{"kind": "http", "response": {"status": 200, "headers": {}, "body": {}, "text": "",
  "elapsed_ms": 12, "api_id": "123", "request": {}},
 "vars": {"token": "t-1"}}
```

### 5.3 执行语义（LowCodeApiCaller）

HTTP：

1. 取 `task.functional.http_apis[api_id]` 快照（缺失→BridgeError）；
2. 应用 override；
3. 运行接口 pre_scripts（独立沙箱，vars 取当前 ctx.vars 快照；pre 写入合并）；
4. HEADER 类环境变量自动注入（接口显式头优先，同声明式）；
5. `http_exec.execute`：模板渲染、cookies、JSONC、binary_ref、egress、证书/
   tls_verify 全部继承声明式语义；
6. 运行 post_scripts（可读 `ctx.response`、可写变量）；
7. 返回响应快照 + pre/post 变量变更；记录 `METHOD url -> status (ms)` 到步骤日志。

gRPC：取 `grpc_apis` 快照 → `request` 深合并 / `metadata` 追加 → `grpc_exec.call_async`
→ `GrpcResponse`。gRPC 快照暂不执行 pre/post（当前 gRPC 数据模型未落脚本列），
保留为后续增量。

嵌套脚本边界：接口 pre/post 脚本运行在独立沙箱，只开放 raw `http_request`，不注入
wrapper 与 api_request，防止 pre→api→pre 递归。

### 5.4 沙箱注入

- `SubprocessBackend.run(..., extra_files={...})` 在 scratch 写 `tp_api_wrappers.py`；
- payload 增加 `http_api_ids` / `grpc_api_ids`（供 `ctx.api` 判别）；
- 仅当 wrapper 源非空时注入；`from tp_api_wrappers import ...` 失败信息保持清晰。

## 6. Copilot

- `gen_grounding.py` 重新生成 schema（LowCodeCase 新字段）与 SDK API 面；
- prompt 规则：生成低代码用例时优先 `ctx.http_api/<api_id>` 或 `tp_api_wrappers.Api<ID>`；
  必须在 `definition.http_api_refs` / `grpc_api_refs` 中显式声明依赖；
- 稳定 ID 优于可读别名（改名不影响脚本）。

## 7. 安全与边界

- 接口快照按 `tenant_id` 解析，不跨租户；
- 所有请求仍走 egress 出口策略、响应限读、请求体上限；
- `tls_verify=false` 仅当接口快照显式配置时生效，脚本不可解除校验；
- 生成源码不落库、不经用户手改；预览端点只读；
- 显式/提取 refs 之外的动态 ID 调用失败，不静默降级为任意请求；
- 项目全量兜底生成有 200 接口上限，超限要求显式声明。

| Copilot | grounding 文件存在、schema 含新字段 |
| Web | pnpm build |

## 9. 验收标准（DoD）

1. 新建接口 id=123，脚本 `await ctx.api("123").run(...)` 可运行，无需知道 method/URI；
2. 生成 `tp_api_wrappers.py` 含 `Api123` 与可读别名；改接口 URI/headers 后脚本零改动重跑生效；
3. cookies/TLS/证书/JSONC/binary_ref/pre-post 与声明式行为一致；
4. 所有测试绿：go test、worker pytest（-W error）、copilot pytest、web build、e2e；
5. 文档、grounding、前端类型全部同步。
